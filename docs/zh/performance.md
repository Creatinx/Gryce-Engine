# 渲染性能：怎么量、时间花在哪、已经修了什么

这份文档记录 2026-10 针对 `test/demo_project/scenes/main.gesc`（3d66 摄影测量城市，
4.37M 顶点 / 1.46M 三角形）做的一次性能排查。示例数字是 RTX 5070 Laptop、
1920×1080、MSAA 4x、SSR+SSAO+IBL 全开的实测值。

---

## 1. 先量，再动手

冒烟程序自带 GPU 分段计时，不需要外部工具：

```bash
./build/GryceRenderSmoke.exe --api opengl \
  --project test/demo_project --scene test/demo_project/scenes/main.gesc \
  --bench 120 --resolution 1920x1080 --no-debug-ui --no-fps --no-vsync
```

输出两块：

```
[gpu] scene                8.333    8.120   86.9%  n=118
[gpu] prepass_normal       0.870    0.849    9.1%  n=118
[gpu] ...
[gpu] 合计(摊到每帧)              9.36
[cpu] 帧耗时 样本=94  平均=11.30ms(88.5 FPS)  中位=...  p99=...
[cpu] 分相平均: RenderWorld=... EndFrame(提交+等GPU)=...
```

判断谁在卡：

- `EndFrame(提交+等GPU)` 明显大于 `RenderWorld` → **GPU 瓶颈**，看 `[gpu]` 分项。
- 反过来 → CPU 瓶颈，看 `[cpu] 分相平均`。
- `[gpu] 合计` 与 `[cpu] 平均` 接近时两个都接近满。

### 笔记本上必须交替 A/B

同一个配置连跑两次能差 2 倍（这台机器 79°C、SM 频率 1762/3090 MHz，功耗墙波动极大）。
任何"改了之后更快"的结论都必须用**同一次会话里交替跑**得出，否则量到的是温度漂移：

```bash
for i in 1 2 3; do
  run A; run B;      # A/B 交替，各自 2~3 次取中位
done
```

同理，`--no-xxx` 这类开关的对照也要交替跑。仓库里两个诊断开关专为此准备：

| 环境变量 | 作用 |
| --- | --- |
| `GRYCE_NO_MESH_WELD=1` | 关闭导入期顶点焊接（对照顶点开销） |
| `GRYCE_FORCE_PCSS=1` | 忽略 PCSS 退化判据，强制保留 blocker 搜索 |

## 2. 时间花在哪（1078p 实测，未优化前）

| 项 | 耗时 | 占比 | 说明 |
| --- | --- | --- | --- |
| `scene` 前向 pass | 11.0 ms | 92% | 天空盒 + 网格 + 不透明/透明物体 |
| ├ PCSS 阴影 | 2.15 ms | 18% | 16 次 blocker 搜索 + 16 次 PCF = 每像素 32 次采样 |
| ├ MSAA 4x | 1.6~2.0 ms | 15% | 4 倍颜色/深度写入带宽 |
| ├ IBL（两 cubemap + LUT） | 0.83 ms | 7% | |
| └ 几何（1.46M 三角形） | ~3.1 ms | 26% | 与分辨率无关：640×360 下仍是 3.1 ms |
| `prepass_normal` | 0.87 ms | 7% | 为 SSAO/SSR 重画一遍几何 |
| SSAO / SSR / bloom / tonemap | < 0.4 ms | 3% | 都很便宜 |

### 几条容易误判的观察

- **降分辨率几乎不省几何开销**：1920×1080 → 640×360 总耗时 10.5 → 4.6 ms，
  但其中 3.1 ms 是几何，顶不掉的。要判断"到底是不是顶点瓶颈"，拿同一个低分辨率
  分别渲染重模型场景和立方体场景：3.29 ms vs 0.22 ms。
- **三角形数不降，焊接顶点救不了几何**。顶点焊接把顶点砍 4 倍，几何只快 3%
  —— 瓶颈是 1.46M 个三角形的装配与亚像素覆盖，不是顶点取值。
- **PCSS 在这种配置下可能完全是白算**（见下）。

## 3. 已经做的三件事

### 3.1 导入期顶点焊接（`engine/assets/mesh_optimizer.*`）

摄影测量 / CAD 导出的网格常常**完全去索引化**：索引缓冲退化成 `0,1,2,3,...`，
每个三角形都带 3 个独立顶点。这个模型 `verts/tris` 恰好等于 3.00。

`AssetManager` 在拿到每种格式的导入结果后统一调 `optimize_imported_mesh()`：

- 按**全部顶点属性逐位相等**（memcmp，哈希只用于分桶）重建索引，绝不做浮点容差合并
  —— 位置/法线/UV/切线/顶点色有任何差异的顶点都不会被合并，所以不会出现 UV 拉伸、
  硬边变软。
- 顺手剔除退化三角形。
- 实测：4.37M → 1.08M 顶点（4.1 倍），顶点缓冲 233 MB → 58 MB，三角形数不变，
  **画面逐像素完全相同（maxDiff = 0）**。
- 收益：GPU 约 3%，显存 175 MB，导入后上传时间同比减少。

日志（每次导入一行）：

```
MeshOptimizer[assimp]: 'xxx' vertices 1408353 -> 351633 (4.0x, 75.2MB -> 18.8MB),
                       tris 469451 -> 469451 (degenerate 0), source was fully de-indexed
```

### 3.2 PCSS 在退化参数下自动退回 PCF（`RenderPipeline::pcss_effectively_enabled`）

PCSS 的 blocker 搜索只为一个量服务：半影宽度。而半影最终被 clamp 到
`[shadow_filter_radius, uPCSSMaxRadius]`，其中下限就是 PCF 用的那个屏幕空间一致半径。

当 `pcss_light_size * pcss_blocker_scale < 1` 时，要算出比 1 texel 更宽的半影，
必须"接收面深度 > 1/(light_size*blocker_scale) 倍的遮挡面深度"，在 CSM 里几乎只
出现在近裁面附近。也就是说 blocker 搜索算完会被直接丢掉。

demo 的 `pcss_light_size = 0.3` 正属此列：**PCSS 开与关的截图逐像素相同
（meanDiff = 0, maxDiff = 0），却要多花 2.79 ms**。现在引擎识别到这种设置会自动
退回 PCF 并打一条日志说明，想真正看接触硬化把 `pcss_light_size` 提到 10~100。

### 3.3 每帧 22 条 "uniform 未找到" 告警

前向 shader 上会无条件写一批只属于延迟管线的 uniform（`uGIMode`、
`uShadowAtlasEnabled`、`uUseSSIL`、`uVSMTexture*` …，共 14 种）。每次
`set_*` 都构造 `std::string`、查哈希表、拼日志、加锁写盘：

```
124 帧里 2760 条告警 ≈ 每帧 22 条
```

现在按 `(setter, uniform)` 只告警一次，并把结论说清楚（"not declared by this
shader (ignored)"），日志立刻干净，GPU 分段计时的输出也不再被异步日志切碎
（之前 `合计` 那一行经常被吞掉，根本没法读）。

## 4. 当前水位

| 配置 | GPU 合计 | 相对 |
| --- | --- | --- |
| 优化前 | 11.98 ms | — |
| 顶点焊接 | 11.7 ms | -3% |
| + PCSS 自动退化 | 9.36 ms | **-22%** |
| + 关闭 MSAA（参考） | 7.3 ms | -39% |

`scene` pass 从 11.04 ms 降到 8.33 ms。

## 5. 还没做的（按收益排序）

1. ~~**LOD / 三角形裁剪**~~：已接入逐物体自动 LOD（见 [lod.md](lod.md)）。导入期生成
   整条 LOD 链，运行时按"几何误差占几个像素"反推切换距离。主 demo 实测
   `lod_pixel_error` 2 → 10 → 20 → 40 对应 GPU 合计 8.00 → 6.60 (-17.5%) →
   4.80 (-40%) → 4.17 ms (-47.9%)。默认 2px 下这个场景不降级（相机 47.5u，L1 误差
   在该距离正好 4.1 像素），要拿性能就抬预算。
   ~~**空间分块 LOD**~~ 也已接入（`assets/mesh_lod.cpp::build_chunked_lod`）：>12 万
   三角形的子网格切成 2³~6³ 空间块，每块各自一条链、各自选级，边界顶点钉住防裂缝。
   **关键判据**：只有"逐块三角形总数明显少于整模当前级别"时才接管 —— 远看时整模
   降一级就够，分块反而更多（主 demo 远视 40px：整模 L3 59k vs 分块 206k）。
   格数不是越多越好：主 demo 近距 16px，2³/3³/4³ 对应 GPU 6.33/6.15/6.48ms
   （4³ 回退是因为格线变密、钉住的接缝顶点变多），默认按"每块 ~2 万三角形"取 3³。
   近看（相机贴着模型，整模判据只能选 L0）实测 16px 预算 **6.17 vs 逐物体 6.84ms
   (-9.8%)、vs 恒 L0 7.25ms (-14.9%)**（4 轮交替取最小值），画面与 L0 平均 \|Δ\| 0.816；
   默认 2px 下一次分块几何都不上传，显存与批次与纯逐物体一致。构建一次性
   ~0.96s / 1.46M 三角形。
   试过但无效：不透明绘制近→远排序（early-Z 友好）。这个场景是三角形装配瓶颈而不是
   填充瓶颈，省不到着色，反而打乱材质绑定顺序 —— 实测慢 4%（6.50 vs 6.26ms），已撤。
2. **深度预通道复用**：现在 `prepass_normal`（0.87 ms）单独画一遍几何，但它输出的深度
   与主 pass 的 MSAA 深度缓冲不是同一张，主 pass 仍然要承受完整 overdraw。把预通道
   深度与主 pass 深度统一（或让主 pass 用 `depth ==` 测试）可以省掉重复着色。
   （预通道现在跟随当前 LOD 级别，不再白付高模几何。）
3. **MSAA 降档**：4x → 2x 省 0.4 ms，4x → 关省 2.0 ms。视觉上是实打实的差别，
   默认没有动；重场景想要帧率可以 `--msaa 2`。
4. **PCSS 真的要开时**：blocker 搜索可以从 16 次降到 8 次（半影是平均值，对采样数不敏感），
   能再省约 0.5 ms。现在默认走 PCF，暂时没必要。
